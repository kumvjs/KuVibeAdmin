# 系统字典一级整树缓存与 SQL 审查

时间：2026-10-02（Asia/Shanghai）。需求标识：system-dictionary-20260930。

## 背景与结论

原实现每次读接口都执行「向上递归算祖先链 + 向下递归查子树」两段 recursive CTE，`hasChildren` 还是每行一次
`EXISTS(SELECT 1 FROM sys_dict c WHERE c.pid = t.id)`。字典是典型读多写少、数据量小、需要任意层级查询的场景，
因此本轮把「读放大」交给 Redis，把 SQL 收敛为单次整树回填。

缓存模型（与需求中「一级整树缓存 + pathIds 裁剪」一致）：

- 一级节点完整无限级子树整体缓存，键 `sys:dict:{tenant}:tree:{一级节点 ID}:{版本号}`，值为扁平行序列（含 `pathIds`、`pathNames`）。
- 版本索引 `sys:dict:{tenant}:index` 保存一级节点列表、每个锚点的当前版本号与一级节点路径快照，**不设过期时间**；
  整树键带过期时间只用于回收孤儿键，逻辑失效完全由版本号负责。
- 读取：`list` 取一级节点全部整树，`list?rootId/rootCode` 与 `detail` 都复用一级整树缓存后在内存按 `pathIds` 裁剪，
  范围裁剪、停用过滤、树/扁平输出全部在内存完成。
- 写入：事务提交后按「受影响锚点的祖先链」递增版本号（含一级节点自身），旧版本键自然不可达；
  改名时清空索引里的名称快照，交由下次读取回源重算。

## 最终读路径

- `loadAncestorPath` 始终以数据库祖先链为准，不做缓存；路径是改名/移动后最容易失真的派生数据。
- `loadTreeRows` 只在整树缓存未命中时执行一次，SQL 内同时算出 `path_ids`、`path_names`。
- `detail` 由「祖先链 + 整树」两次查询降为「祖先链 + 一次缓存读取」，`hasChildren` 从完整一级整树推导。
- `effectiveStatus` 由缓存行的祖先链在内存中计算，停用分支整体裁剪。

## 失效协议

写操作在事务内收集 `bumpedRoots`（受影响锚点及其祖先链，带名称与是否一级节点），提交后调用
`DictCacheService.invalidate`。失效用一段 Lua 完成：

1. 乐观锁校验：参数里带「写入前读到的版本号」（新锚点用哨兵 `-`），任一版本已被并发写入者改变就整体放弃，
   避免旧快照覆盖并发的失效结果；
2. 写入递增后的版本号，并按名称维护一级节点路径快照（改名时清空，交由下次读取重建）；新建一级节点同时登记到 `roots`。

路径解析不做缓存，因此失效协议里没有逐节点路径键清理；改名/移动靠祖先链版本号递增让旧整树键不可达。

索引被人工删除或 Redis 换库时脚本返回 0 并告警，下次读取会用随机新版本号重建索引，旧键不可达。

## SQL 与索引审查

- 保留 `idx_sys_dict_pid`；`uq_sys_dict_code` 是全局编码唯一定位索引，`resolveNodeId` 走它。
- 未增加 `full_path_ids`/GIN/表达式索引：路径是只读派生数据，回源只在缓存未命中时发生，写入侧不再需要级联重写。
- `ORDER BY t.path_ids` 去掉读侧排序开销；`path_ids::text[]` 保证 bigint ID 全程字符串、不丢精度。
- 未改变表结构与迁移文件，本轮无迁移。
